## 0. Executive Summary

| 관점 | 요약 |
|---|---|
| **문제 (Problem)** | 문서를 넣으면 편집 가능한 PPTX가 나오는 파이프라인은 이미 작동한다. 그런데 결과물을 받기까지의 과정에서 대표가 "이거 왜 이래?" 하고 개입해야 하는 순간이 한 세션에 네 번 이상 있었고, 그중 가장 비싼 것은 화면이 아니라 **에이전트의 판단 실수**였다 (고객 CI 색을 강등, 불가능한 재배치를 약속해 8페이지 폐기, 검사 출력을 잘라 "0 errors"로 오판, 표 3개 소실을 경고 없이 통과). |
| **해결 (Solution)** | 네 축을 한 번에 재구축한다. ① 제작 사고과정: 판단 규칙을 프롬프트 계약에 명문화하고, 되돌릴 수 없는 비용이 큰 판단은 코드 게이트로 강제. ② 플로우: 단계 전환 지연을 숨기고 진행을 보여주며, 서버가 대기 중 죽지 않게 하고, 이전 단계로 돌아갈 수 있게. ③ UI 편의: 스크롤 리스트를 "책처럼" 넘기는 구조로 3단계 일괄 전환. ④ 유려함: 대기·미리보기가 항상 "지금 무엇을 하는지"를 말하게. |
| **기능·UX 효과 (Effect)** | 대표가 덱을 만든 뒤 뒤집는 일이 사라지고, 확인 3단계가 한 호흡에 끝나며, 실습생이 아무 맥락 없이도 첫 덱을 완주한다. |
| **핵심 가치 (Core Value)** | "만든 뒤 뒤집을 필요가 없는 산출물을, 근거를 눈으로 보면서, 예측 가능한 시간 안에." 상용 도구가 줄 수 없는 것 — 고객 CI·구조 판단 기준을 우리 손으로 정의하고, 데이터는 로컬에 남는다. |

한 문단으로: 이번 재구축은 SVG를 더 잘 그리는 일이 아니다 (대표가 그 부분은 괜찮다고 했다). **에이전트가 확인 없이 단정하는 습관을 끊고, 확인 화면이 대표의 검토 리듬에 맞게 움직이게 만드는 일**이다. 가장 큰 설계 질문은 하나다 — "프롬프트 규칙으로 충분한가, 코드 게이트가 필요한가". §8.1에서 답한다.

## 1. 배경

### 1.1 제품이 무엇인가

`slide-master` / `ppt-master`는 앱이 아니라 **Claude Code 스킬 패키지**다 (Python 스크립트 + Markdown 프롬프트 계약). AI 에이전트가 사용자 PC에서 정해진 절차를 따라 원본 문서(PDF / DOCX / MD / PPTX / URL / 주제 한 줄)를 네이티브 편집 가능한 PowerPoint로 만든다.

```
Source → 프로젝트 생성 → [템플릿 설치] → Strategist 3단계 확인(브라우저 UI)
       → [이미지 생성] → Executor SVG 작성 → 품질검사 → PPTX 내보내기
```

3단계 확인(SKILL.md Step 4)은 브라우저 위저드다. Stage 1 = 방향(템플릿 카드, 캔버스, 청중, 모드·비주얼 스타일). Stage 2 = 디자인 시스템(쪽수, 색, 아이콘, 타이포, 수식). Stage 3 = 이미지·실행 방식. 단계 사이마다 에이전트가 `result.json`을 읽고, 덱 템플릿이 골라졌으면 지연 설치(구조 preflight 포함)를 하고, 확정된 앵커로 다음 단계 후보를 다시 도출해 `recommendations.json`을 덮어쓴다. 확인 서버는 Flask (`127.0.0.1:5050+`), **유휴 900초 후 자동 종료**, `--wait` 예산 590초.

### 1.2 저장소 현황 — 브리프 이후 바뀐 두 가지 사실

1. **파이프라인이 이제 우리 것이다.** `wedraw-ricky/slide-master`가 `origin`, `byungjunjang/slide-master`가 `upstream`으로 잡혀 있다 (`git remote -v` 확인). 따라서 **파이프라인 수준의 수정(프롬프트 계약, 스크립트, 서버)이 이번 범위에 들어온다.** 이전에는 오버레이만 손댈 수 있었다.
2. **저장소가 둘이다.** 오버레이 `wdb-ppt-ui`(45파일)와 포크(12,333파일)는 별개 저장소이고 둘 다 대표 소유다. 오버레이는 업스트림 확인 서버를 import한 뒤 네 지점(`__file__`, `_CATALOGS_PATH`, `static_folder`, `_DECKS_DIR`)만 돌려놓는 구조라 업스트림을 한 줄도 고치지 않는다. **두 저장소를 합칠지는 열린 결정이다** (§12). 이 문서는 결정하지 않으며, 각 문제마다 "어디에 있는가"를 둘로 나눠 적어 어느 쪽을 택하든 쓸 수 있게 한다.

### 1.3 범위 — 대표가 정한 것

| 구분 | 내용 |
|---|---|
| **IN** | 플로우 (단계 간 흐름) / 유려함 (다듬어진 정도) / UI의 편리함 / **제작하는 사고과정에서의 보완점** (에이전트의 판단 — 대표가 직접 지목) |
| **OUT** | 제작 단계 자체와 결과물 품질 — SVG 저작, 내보내기 품질. 대표가 "괜찮다"고 했다. 이 문서의 어떤 해결책도 여기를 건드리지 않는다. |
| **PARKED (백로그)** | "비율에 맞게 스타일을 유지하되, 각 사이즈마다 성향이 다르니 구분하면 좋겠다" — A4 문서 / 16:9 발표 / 9:16 세로가 하나의 아이덴티티 안에서 서로 다른 타이포·레이아웃 본능을 갖는 것. §13에 기회로만 기록. |

### 1.4 이 문서가 답하는 질문

- 어떤 문제가 있고, 각각 얼마나 비싼가 (증거 기준)
- 어디에 있는가 — 포크 파이프라인인가, 오버레이인가, 둘 다인가
- 고치면 대표·실습생·에이전트에게 무엇이 달라지는가
- 대표가 순위를 매길 수 있는 목록 (§14)

| | 도움 | 해로움 |
|---|---|---|
| 내부 | 오버레이 4지점 리다이렉트 구조 / `result.json` 계약 / 완전 로컬 / 양쪽 MIT / 프롬프트 계약이 코드와 분리돼 배포 없이 규칙 수정 / 문제가 "규칙 부재"로 재현 가능해 진단이 명확 | 에이전트 판단은 단위 테스트 불가 / §e에 CI vs 템플릿 우선순위 없음 / 변환 프로파일에 소스 비교값 없음 / idle 900s가 검토 리듬과 충돌 / 역방향 전이 없음 / 설치 시 템플릿 린트 없음 |
| 외부 | 업스트림 개선 흡수 / 실습생 공개가 문서화 압력 / 대표가 다음 요구(캔버스별 성향)를 이미 예고 | 2단계 업스트림(byungjunjang → hugohe3) 드리프트가 리다이렉트 지점·계약을 깰 수 있음 / 판단 회귀는 사람 검증에만 의존 / 상용 SaaS의 UI 편의성이 실습생 이탈 유인 |

- **SO**: 오버레이 무수정 구조로 업스트림 개선을 계속 흡수하면서, 실습생 온보딩 압력을 프롬프트 계약 정비 기회로 전환 — CI 우선순위 규칙 채우기를 온보딩 문서화 과제로 묶는다.
- **WT**: 판단 회귀가 테스트 불가하므로, 실습생이 매 세션 "규칙이 지켜졌는가" 체크리스트를 돌리게 해 사람 검증으로 보완하고, 업스트림 드리프트 시에도 계약 위반을 빨리 잡는다. **단, 되돌릴 수 없는 비용이 큰 판단(캔버스 불일치, 표 소실)은 사람 검증에 맡기지 말고 코드 게이트로 올린다** (pm-lead 보강).

### 6.5 Build vs Adopt

Porter's 5 / PESTLE은 내부 도구라 해당 없음. 포크+오버레이 유지 vs SaaS 전환은 실제 결정이므로 짧게:

| 축 | 포크 + 오버레이 유지 | SaaS 전환 |
|---|---|---|
| CI·구조 충실도 | 규칙을 직접 명문화 | 벤더 로직에 종속 |
| 데이터 위치 | 완전 로컬 — 한수원 등 대외비가 밖으로 안 나감 | 외부 업로드 |
| 유지보수 | 대표·실습생이 계약을 관리 (비용) | 구독료 |
| 온보딩 가치 | 저장소를 읽고 고치는 것이 학습 | 사용법만 배움 |

**판단: 유지.** 결정적 이유는 대외비 로컬 처리와, "CI 우선" 같은 위드비 고유 기준을 프롬프트 규칙으로 직접 통제할 수 있다는 점. SaaS의 UI 편의성은 오버레이 리디자인의 참고 자료로만 쓴다.

### 7.2 시장 규모 — 한 문단

TAM/SAM/SOM은 이 결정에 관여하지 않는다. 이 제품은 판매하지 않는 내부 도구이자 실습생 온보딩 도구이고, 사용자는 대표 1명 + 실습생 수 명 + 에이전트다. 근거의 원천은 실제 프로젝트 2건(KHNP, speakup)뿐이다. 의미 있는 숫자는 시장이 아니라 **위드비가 월간 이 파이프라인으로 만드는 덱 수, 덱당 재작업 시간, 실습생 콜드 스타트 성공률**인데 셋 다 현재 집계되지 않는다 (`확인 필요:` — 세션 로그의 "폐기 후 재생성" 빈도와 토큰 사용량으로 집계 가능). 시장 숫자를 지어 넣지 않는다.

### 7.3 사용자 감성 — 저장소 안에서 찾은 것

정량 감성 데이터는 없다. 저장소에 있는 진짜 피드백은 두 곳뿐이다 (pm-research): `docs/why-ppt-master.md`의 유지관리자 자기 평가("Setup required", "Slower generation — 10–20 min", "No full freeform canvas")와 `docs/faq.md`의 "'just a toy'라는 말이 맞나?" 항목. 후자에서 유지관리자는 품질 편차를 "harness + model = agent" 프레임으로 모델·컨텍스트 탓으로 돌린다. **이 프레임이 위험하다** — E-1~E-5 같은 계약 공백(우선순위 미정의, 출력 절단)이 "모델 탓"으로 흡수되면 계약 자체의 결함이 영영 드러나지 않는다. §10 사전 부검 6번.

### 8.1 설계 원칙 — 규칙인가, 게이트인가

§5의 핵심 질문에 대한 이 문서의 답:

> **되돌릴 수 없는 비용이 큰 판단은 코드 게이트로, 나머지는 프롬프트 규칙으로. 프롬프트 규칙은 실험(E1)으로 실효성을 확인하고, 실패하면 게이트로 격상한다.**

| 판단 | 비용 | 형태 |
|---|---|---|
| 캔버스 ≠ 템플릿 `canvas_format`인데 구조 경로 진입 | 8페이지 폐기 | **게이트** (설치 preflight 하드 스톱) + 규칙 |

## 13. 백로그 — 캔버스 크기별 스타일 성향 (v1 제외)

대표의 말: "비율에 맞게 스타일을 유지하되, 각 사이즈마다 성향이 다르니 구분하면 좋겠다."

기회: A4 문서(읽는 물건)·16:9 발표(보는 물건)·9:16 세로(스크롤하는 물건)는 같은 팔레트·서체 안에서 여백, 정렬, 글자 급수 사다리, 정보 밀도의 본능이 달라야 한다. 지금은 `visual_style` 18종이 캔버스와 무관하게 하나의 레이아웃 언어를 갖는다.

`추정:` 후보 해법 (pm-discovery) — (M) `visual_style` 프리셋에 `canvas_format`별 서브 프로파일을 얹어 팔레트·서체는 공유하고 여백·정렬 본능만 분기 [포크]; (N) Stage 1에서 캔버스가 확정된 뒤에만 "성향" 후보를 노출 [둘 다]. 이 브랜치는 `structured-templates.md`의 `canvas_format` 고정 계약과 같은 뿌리(E-2)이므로, R-T3 게이트가 자리 잡은 뒤에 착수하는 것이 안전하다.
