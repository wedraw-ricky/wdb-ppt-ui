## Executive Summary

**"판단해야 할 자리에서 조용히 넘어가던 것"을 전부 멈춰 세웠고, 기획이 "무엇을 할지"에서 끝나지 않고 "언제·누가·얼마로"까지 가게 만들었다.**

| 관점 | 내용 |
|---|---|
| **문제** | 에이전트가 근거가 둘일 때 조용히 한쪽을 골랐다. 캔버스가 안 맞는데 여덟 쪽을 만들고 버렸고, 고객 색을 두고 템플릿 색으로 냈고, 표가 사라진 걸 아무도 몰랐다 |
| **해결** | 되돌리기 비싼 판단마다 게이트를 세웠다. 확실할 때만 멈추고, 애매하면 사람에게 묻는다 |
| **효과** | 폐기 쪽수 0을 겨냥한 게이트 4건 + 강의 규칙 검사 11건. 사람이 확인할 것은 다섯 줄로 줄었다 |
| **가치** | 도구가 강의를 대신하지 않는다. **강의가 가르치는 순서를 도구가 지키게** 했다 |

## 대표 우선순위 — 14건 전부

| 번호 | 무엇 | 어떻게 |
|---|---|---|
| 1 | 캔버스 ≠ 템플릿인데 진행 | 설치 **전에** 멈추고 두 선택지. 부분 설치 없음 |
| 2 | 고객 CI 색이 템플릿 색에 밀림 | 조직명 + CI 가 있으면 CI 가 주색 |
| 3 | 검사 출력이 잘려 "문제 없음"으로 보임 | 결과 줄을 요약 앞뒤 + 별도 출력으로 |
| 4 | 표 소실을 아무도 경고 안 함 | 원본 표·이미지 개수를 세어 비교, 불일치면 정지 |
| 5 | 확인 화면이 기다리다 서버가 죽음 | 화면이 열려 있는 동안 신호를 보냄. 두 번 놓치면 띠 표시 |
| 6 | 뭘 하는지 안 보임 | 지나가는 지점마다 한 줄. 개수·퍼센트는 안 씀 — 재는 것이 없어 지어내는 것이 되므로 |
| 7 | 단계 전환이 느림 | 기다리는 동안 다음 단계를 미리 뽑고, 가정이 맞으면 그대로 씀 |
| 8 | 확인 폼이 4088px 스크롤 | 한 화면에 한 질문. 레일이 지도가 됨 |
| 9 | 설치 문서가 첫 줄부터 어긋남 | 어제 완료 |
| 10 | 템플릿 결함을 등록 때 못 잡음 | 글자가 배경에 파묻히거나 캔버스 밖이면 등록 거부 |
| 11 | 서체 진실이 둘 | 한 문서 안에 정반대 지시가 둘 다 "필수"였다 → 우선순위 표 하나로 |
| 12 | 확정한 단계로 못 돌아감 | 확정 값 조회 + 무엇이 무효가 되는지 계산 |
| 13 | 규칙 준수를 확인할 수단 없음 | README 에 체크리스트. 기계가 보는 것과 사람이 볼 것을 나눔 |
| 14 | 한 단계만 고쳐지는 일 재발 | 프리뷰 필드 계약을 산문에서 코드로. 어기면 테스트가 필드 이름을 댐 |

## 강의를 읽고 바꾼 것

교안 165장과 녹취 4차시를 계약과 대조한 결과다.

### Planning → Making → Presentation

교안 26쪽의 3단 구조를 그대로 단계로 삼았다.

- **기획이 "무엇을 할지"에서 끝나지 않는다.** 클라이언트 블록 8항목만 있고 컨셉·플래너 블록이 없었다. 이제 언제·누가·얼마로 하고 무엇이 틀어질 수 있는지까지 간다 (8절 → 12절).
- **문서는 골격이 아니다.** 사람이 받는 기획서는 교안 121쪽의 항목으로 묶는다. **묶기만 하고 요약하지 않는다** — 문장을 줄이는 것은 기획하는 쪽 일이다.
- **발표 순서는 자유, 결론은 하나.** 순서는 상황마다 달라야 하지만 도착점이 어긋나면 멈춘다.
- **기획부터 할 일과 아닌 일이 갈린다.** 강의 교안이나 이미 정해진 자료는 이 코스를 탈 이유가 없다. 인터뷰에 질문을 더하지 않고 골격에서 파생된다.

### 검사 11건

확실한 것만 멈추고, 사람 판단이 섞이는 것은 알리기만 한다. **맞는 기획서를 막는 검사는 결국 아무도 안 본다.**

| 멈춤 | 알림 |
|---|---|
| 대목적을 목적으로 씀 · 현상/영향/원인 중복 · 과제에 기한 없음 · 결론 어긋남 | 기대효과가 영향보다 김 · 목적이 여럿 · 비교 기준 없는 수치 · 개발 요건 |

**만들지 못한 것 2건**은 숨기지 않고 적어 두었다 — 지시사항 원문을 아무 데서도 묻지 않아 만들 수 없는 검사 하나, 사람 판단이라 규칙으로 못 만드는 것 하나.

## 이번 사이클에서 배운 것

**같은 것이 두 곳에 손으로 적혀 있으면 언젠가 어긋난다.** 이 결함을 하루에 세 번 만났다.

| 어디 | 어떻게 드러났나 |
|---|---|
| 수치 판별 규칙 | 같은 이름으로 두 번 정의해 앞이 죽었다. 제목 검사가 `2026년` 을 수치 없음으로 봤는데 **테스트 217건이 전부 통과하고 있었다** |
| 프리뷰 필드 | 산문에만 있어 1단계가 2단계 필드를 읽었고, 1단계만 먼저 다시 그려졌다 |
| 단계 분류 | 서버(파이썬)와 화면(타입스크립트)에 각각 |

셋 다 **대조하는 검사**로 닫았고, 각각 일부러 어겨서 실제로 잡히는 것을 확인했다. 통과하는 것과 잡는 것은 다르다.

**설계 문서는 코드보다 늦는다.** 대조해보니 일치율 77% 였고, 어긋난 이유는 코드가 틀려서가 아니라 **설계가 적게 적고 있어서**였다 — 있지도 않은 주소 네 줄, 검사 25개 중 13개만. 설계를 코드에 맞춰 v1.7 까지 올렸다.
